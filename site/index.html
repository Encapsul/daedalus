How it works

Three things it actually gets right.

Language-agnostic

Not tied to one runtime.

x.bin packages a rootfs, not a language ecosystem. It detects app.py, package.json, or a native ELF binary, then bundles the interpreter, shared libraries, and your code together. A pure-Python ELF analyzer resolves DT_NEEDED chains recursively — no host ldd required.

$ xbin build ./app -o app.xbin
detecting runtime: python3.12
resolving .so via ELF parser (DT_NEEDED)
packaging 2 layers · zstd -19
✓ app.xbin ready (7.1 MB)
Incremental rebuilds

Only what changed gets rebuilt.

The payload is split into two independent layers: a runtime layer (interpreter, stdlib, shared libraries) and an app layer (your code + site-packages). Each layer is a zstd(tar) blob with its own SHA-256. Editing your code doesn't recompress the whole rootfs — only the small app layer rebuilds.

initial build (cold cache)
runtime layer: 54 MB raw → 11.9 MB zstd 25.1s
✓ done in 25.1s
rebuild — app code changed
runtime layer: cached (SHA-256 match)
app layer: 0.2 MB → 0.0 MB
✓ done in 1.2s
Signed before extraction

Verified before a byte hits disk.

The v3 footer carries a sig_offset pointing to a 68-byte Ed25519 signature block. The Rust launcher reads the footer, verifies the signature against trusted keys in ~/.xbin/trusted-keys/, validates SHA-256 integrity, and only then extracts. An invalid or missing signature means nothing gets written.

$ xbin verify app.xbin
✓ Ed25519 signature verified
trusted key a3f9…21be
$ xbin verify tampered.xbin
× signature invalid — refused
Layer system

Two layers. One cache key each.

Each layer is a self-contained zstd(tar) blob. The runtime layer is keyed by SHA-256 of its uncompressed tar — if the hash matches, the compressed blob is reused from ~/.cache/xbin/build/. The app layer always recompresses.

ELF launchermusl static, ~600 KB
runtime layerzstd(tar) — interpreter + .so + stdlib
app layerzstd(tar) — code + site-packages
metadataJSON (entrypoint, env, layers[])
signature block68 bytes (v3 only)
footer92 bytes — the whole format spec

What goes in each layer

Runtime layer contains the interpreter binary (/usr/bin/python3.12), Python stdlib (/usr/lib/python3.12/), all shared libraries discovered by the ELF analyzer, and minimal /etc files.

App layer contains your source code in /app/ and third-party packages in /app/site-packages/. Both layers are deterministically tarred (sorted entries, mtime=0, uid=0) so identical content produces identical bytes.

The format

A 92-byte footer
describes the whole file.

The footer sits at EOF and is versioned — a v2 launcher reads the last 84 bytes, sees format_version = 3, and cleanly reports an unsupported version. format.rs and format.py stay byte-for-byte in sync.

Designed for backwards compatibility

The last 84 bytes of a v3 footer are byte-identical to v2. A v2 launcher reading EOF-84 sees the correct magic and version number, and cleanly rejects the file. The 8-byte sig_offset prefix is only read by v3-aware launchers.

The footer sentinel 0xBEEFCAFE acts as a validation marker — the launcher reads backwards from EOF, finds the sentinel, then parses forward.

Security

Nothing touches disk
before integrity is verified.

Ed25519

Cryptographic signatures

Keygen, sign, verify. The launcher checks Ed25519 signatures against trusted keys in ~/.xbin/trusted-keys/ before extraction. 64-byte signatures, 32-byte public keys.

SHA-256

Payload integrity

The footer stores a SHA-256 hash of layers + metadata. The launcher recomputes it on every run. Corrupted or tampered files are rejected before extraction begins.

pivot_root

Filesystem isolation

Run with --isolation 2 for user namespaces + pivot_root + seccomp. The app sees only its own rootfs. No root required — unprivileged, kernel-enforced.
